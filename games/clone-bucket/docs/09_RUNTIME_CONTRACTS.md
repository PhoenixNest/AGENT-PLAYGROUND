# 09. Runtime Contracts (clone-bucket rebuild)

**Status:** Reviewed by the lead 2026-11-07; decisions in §5 settled. **2026-11-08:** all debug code was removed from the rebuild (§3.8).
**Purpose:** one shared contract for the parallel developers who write method bodies inside the recovered game classes. For every class it says what each method is for, who calls it, what it calls, what events it raises or hears, what state it changes, and how sure we are. Names are the recovered names, exactly as in code.
**Scope:** the 148 game `.cs` files under `games/clone-bucket/unity/clone-bucket/Assets/Scripts/Assembly-CSharp/`, plus the 3 CrazyLabs database classes the game uses (`DatabaseController`, `DataSetConfig`, `DatabaseConfig`). Excluded: `Tabtale`, `CrazyLabs` (other than those 3), `TTPluginsAssetBundles`, `UnityEngine`, `Properties`.
**Companion docs:** `01_SYSTEM_ARCHITECTURE.md`, `02_GAMEPLAY_MECHANICS_SPEC.md`, `03_LEVEL_DESIGN_AND_DATA_SPEC.md`, `04_PHYSICS_AND_RENDERING_SPEC.md`, `06_SKIN_AND_ECONOMY_SPEC.md`, `08_IMPLEMENTATION_PLAN.md`.

## 0. Tags and evidence

| Tag             | Meaning                                                                                                                                                           |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **[Recovered]** | Read from a signature, field, enum, serialized value, scene or prefab, or a spec. Source given where useful.                                                      |
| **[Inferred]**  | Deduced from a name, a UnityEvent wiring, a serialized reference or a spec sentence. The reason is given.                                                         |
| **[Decision]**  | A choice we make because the original logic is lost. Each one is simple, and each has a play-test to confirm it. The decision codes D1 to D26 are listed in §3.6. |

**What the export does not contain.** Every method body is a stub. A grep for calls such as `LevelsController.`, `GameManager.instance`, `BallsController.` or `EventManager.` finds **no call sites** in the game code. The sources for those entries are, in order: the UnityEvent wiring in `Main.unity` and the prefabs (§0.1), the serialized references, and the specs. Owners must treat these as design intent and confirm them against the spec before relying on them. No call edge in this document is a recovered fact.

## 1. Runtime flows

Each step is `Class.Method`, what happens, and the data passed. Steps marked **[Inferred]** rest on the wiring or the spec, not on code.

### 1.1 Boot (Loading.unity, then Main.unity)

1. [Inferred] Unity loads `Loading.unity`. Awake order: `DatabaseController.Awake` → `InitializeDatabase()` → `TryOverrideDataSetsWithRemoteFiles()` (use remote `LevelsData.csv` if the remote feature `LevelFunnel` delivers it; otherwise the bundled `TextAsset`) → `InitializeAllDataSets()` → `ParseDataSet(dataSet)` per `DataSetConfig` → `DatabaseController.OnInitialized` raised and `IsInitialized` = true.
2. [Inferred] `RemoteConfigHelper.Awake` sets `Instance`. It starts `TimeOutRemoteConfig(remainingTime)` with `RemoteTimeOut`. When the SDK reports ready, `OnRemoteConfigReady(bool)` sets `isRemoteReady` and raises `OnRemoteReady(bool)`. On timeout it raises `OnRemoteReady(false)`.
3. [Inferred] `WaitForRemoteConfigReady.LoadMainGameScene(bool)` listens for `RemoteConfigHelper.OnRemoteReady`, then loads `sceneName` (`Main`). Note: this component is not attached to any scene (§0.2), so this step is a design intent. Confirm the boot route with the lead (Q3).
4. [Recovered] `LoadingScene.Awake` sets `_loadingTimer` = 0 and `_isLoading` = false. `LoadingScene.Update` ticks the timer. `LoadScene()` (coroutine) loads Main asynchronously and reports progress into `_image.fillAmount` (`_image` is serialised). At `_timeout` = 10 s, `HandleLoadGameOnTimeout()` forces `LoadGame(true)`. On completion, `LoadingScene.OnLoadingComplete` is raised.
5. [Inferred] Main.unity opens. `GameManager.Awake` (via `SingletonBehaviour<GameManager>.instance`) → `LoadData()` reads the save (§3.5) → `SaveData(level)` is written back if the format was upgraded → `GameManager.Start` shows `MainScreen` (`Close` on the other screens).
6. [Inferred] `SkinManager.Awake` builds the skin list from `_configs` (3 `ShopConfig` assets). `ColorSchemeController` is created by `ColorSchemeInstaller` with `ColorSchemesConfig` (5 schemes). `MaterialManager.Awake` (`SingletonBehaviour`) prepares the theme. `AudioManager.Awake` and `HapticManager.Awake` read `GameManager`'s sound and haptic flags.
7. [Inferred] `TTPManager.Awake` keeps the instance across scenes. SDK initialisation happens in the SDK; game code only calls the wrapper methods (see §3.8).

### 1.2 Level load (data row → prefab → balls)

1. `MainScreen.StartPlayClick()` → `GameManager.StartPlay()`. If `GameStarted` is already set it returns. Otherwise it sets `GameStarted` = true and `LevelCompleted` = false, calls `MainScreen.Close(OnMainScreenClosed)`, then switches the `Tutorial` hint off. The main screen tweens out over 0.5 s (R7 §5). When the close ends, `OnMainScreenClosed` turns the main screen off, calls `ShowGameScreen()` (screens only) and `RefreshGameScreen()` (`SetLevel`, `SetBalls(total)` as the counter target, `SetProgress(0)`; the counter then counts up in `GameScreen.Update`, R7 §5.6). The level is spawned earlier, by `Reset` (`LevelsController.Spawn(CurrentLevel)`), not by `StartPlay`.
2. `LevelsController.Spawn(int)` (static, async void) → `LoadData()`:
   - Reads the live list: rows of `DataSetId` `"LevelsData"` through `DatabaseController.GetString/GetInt`, filtered by the live-order rule (doc 03 §4). Row at index `playerProgressIndex` is the current row. [Decision] D1.
   - Sets `CurrentLevelData` (a `LevelData`: `miniLevelNames`, `isLooping`, `levelDifficulty`, `backgroundMaterialName`).
   - Sets `TotalMiniLevelCount` and `TotalNonLoopingMiniLevelCount`. Fills `_miniLevels` and `_miniLevelsByNames`.
3. `LevelsController.SpawnLevelPrefab()` → `Instantiate` the prefab `Resources/prefabs/minilevels/<Level Name>.prefab` under `LevelsConfig.prefab` (`LevelView`). For `LevelType.Json` rows only: instantiate `LevelsConfig.jsonBaseLevelPrefab` and call `MazeJsonGenerator.ApplyFromJson(json)`. The shipped table has only `Prefab` rows. Before the previous level is cleared, `LeanPool.DespawnAll()` runs, as in the original `LevelsController.Spawn`.
4. `LevelsController.StartMiniLevel(isFirstChunk: true)` → `MiniLevelIndex` = 0. Creates a `MiniLevelData` from the row (`startBallAmount`, `targetBallAmount`, `perfectBallAmount`, `isBossLevel`, `levelType`, `gateTypes`, `gateValues`, `mazeMaterialName`). Sets `TotalBallCountInMiniLevel` = 0 and `TotalFillCount` = 0 and `FilledStarCount` = 0. Target and Perfect come from the row ([Decision] D2).
5. `LevelsController.RequestSpawnInitialBalls()` → for `i` in `0..startBallAmount-1`, `BallsController.Spawn(LevelsConfig.ballSpawnPositions[i % 20], miniLevelView.ballsParentInsideMaze)`. Positions cycle over the 20 spawn points ([Decision] D24; Q13). `BallsController.Spawn` takes its ball from `BallsPool.Get()`. Boss prefabs leave `ballsParentInsideMaze` unset. The original passes it on unconditionally (a null parent is the scene root), so the rebuild does too. A null check there used to skip the balls of every boss level.
6. `LevelsController.SetControllerActive(true)` and `SetControllerEnabled(true)` enable the `RotateController`, the `Bucket` and the `MiniLevelView`.
7. `CameraMove.Reset()` → `AddBall(ball)` for each spawned ball. `CameraMove.Start` (coroutine) waits for the first frame, then sets `defaultPos`, `defaultOrthoSize` and `defaultFOV` from the Main Camera.
8. `LevelsController.OnLevelSpawned` is raised. `GameScreen` listens (inferred): `SetLevel(CurrentLevel + 1)`, `SetBalls(startBallAmount)` (sets the counter target only, R7 §5.6), `SetProgress(0)`. `LevelChunkVisualizer` and `ChunkStarBar` set up the header; both show only when the level has more than one mini-level (`tools/recovery/recovered/R6_header_ui.md`).
9. `TTPAnalyticsService.MissionStarted(missionIndex)` and `GameManager.SendMissionStart(missionIndex, chunkIndex)` (analytics) are called at step 4 ([Inferred]).

### 1.3 Play loop (per physics step and per frame)

1. **Input.** Each level prefab has a Lean component whose `onDelta` event calls `RotateController.RotateAB()` (recovered, `tools/recovery/recovered/R3c_reference_point.md`). `RotateAB` reads `LeanTouch.Fingers[0]` and rotates `Target` at once: `Transform.Rotate(Axis, dist × degrees × Multiplier, Space)`. `degrees` is `LeanFinger.GetDeltaDegrees`. `dist` is the finger's distance from the target × 0.25, capped at 1 when `Targets` is not empty (boss levels). It then records the change in `remainingDelta` and restores the old local rotation (the Lean Touch `LeanRotateCustomAxis` pattern). The mapping is linear in drag × `Multiplier` ([Decision] D12, now recovered; Q5 closed).
2. **Rotation.** `RotateController.FixedUpdate()` calls `UpdateRotation(LeanHelper.GetDampenFactor(Damping, Time.deltaTime))`. The decompile shows that helper's result as an unused call. The value stays in the float argument register, and `UpdateRotation` reads it as its factor (read from the calling pattern, medium-high; `tools/recovery/recovered/R3_rotation_camera.md` A.5). `UpdateRotation` computes `newDelta = Slerp(remainingDelta, identity, factor)`, sets `localRotation = localRotation × Inverse(newDelta) × remainingDelta` on `Target` and on each `RotateTarget`, then sets `remainingDelta = newDelta`. `Target` is the maze rotator on the 102 non-boss levels and `GameManager.ReferencePoint` on the boss levels, where `Awake` sets it when `Targets` is not empty. The `RotateTarget` formula is above for `Dir` 1. For any other `Dir` (the shipped boss targets use −1) it is `localRotation × Inverse(remainingDelta) × newDelta`. `RotateToDefault()` snaps `Target.rotation` to identity; it does not ease.
3. **Balls, per FixedUpdate (0.033 s).** `BallsController.FixedUpdate()` loops over `_allViews`. For every active ball it calls `HandleSpeedOnFinishSpace(view)` and then `HandleRotation(view)`. There is no boss branch, as in the original.
   - `HandleRotation(view)` (static) keeps the ball's Z position at 0 and its rotation in Z only (the `Ball` prefab constraints). It sets `view.skinRotator.rotation = Quaternion.Euler(0, 0, eulerAngles.z)`, so the skin turns with the ball (as in the original). It is also where the speed cap is applied.
   - If the ball is in the maze, its speed is capped at `inMazeMaxSpeed` (10). Outside the maze the cap is `outMazeMaxSpeed` (40). Both come from `BallsConfig`. The unit is [Unknown] (Q6). [Decision] D11: cap the Rigidbody's `linearVelocity` magnitude.
   - `HandleSpeedOnFinishSpace(view)` acts when `BallData.inFinishSpace` is set. `HandleBossLevelRotation` is not called, because the original never calls it.
4. **Trigger dispatch.** The `Ball` prefab's `BallView.OnTriggerEnter(Collider)` raises `OnTriggerEntered(Collider)`. `BallsController.OnBallTriggerEntered(view, other)` branches on the other collider's tag:
   - `Multiplicator` → `BallsController.Multiply(view, multiplicator, other, parent)` returns true if the ball was cloned. Gate effect: `Multiplicator.MultiEffect()`.
   - `SubGate` → `SubGate.Sub()`: while the gate's value is at least 1, it lowers the value by 1 and returns true, and the ball is removed with `BallsController.Despawn(view)`. `Despawn` subtracts the ball's full value from the total. When the value is below 1, `Sub()` hides the gate's visual, collider and label and returns false, so the ball passes (as the original `SubGate.Sub`). Effect: `SubEffect` from `GameManager.SubEffectPool`.
   - `DivideGate` → `BallsController.Divide(view)` (static) → `DivideGate.Divide(BallView)`. Effect: `DivideEffect` from `GameManager.DivideEffectPool`.
   - `BucketFillTrigger` → `Bucket.OnFill(filledBefore, 1)`.
   - `BucketDestroyTrigger`, `DestroyTrigger` → `BallsController.Despawn(view)`.
   - `BucketShakeTrigger` → `Bucket.Shake()`.
   - `FinishSpace` → `HandleSpeedOnFinishSpace(view)`.
   - `ChainTrigger` (the trigger is on the chain, not the ball): `ChainTrigger.OnTriggerEnter` checks tag `Ball` and calls `Chain.ChainUpdate()`.
   - `ForbiddenArea.OnTriggerStay(other)` pushes the ball toward `targetPoint` ([Inferred] from the name and the field).
   - `OnBallTriggerExited` → `BallsController.OnBallTriggerExited`, which leaves the ball's gate history unchanged (step 5).
5. **Gate re-trigger guard.** A ball records each gate collider it has already passed in `_ignoredMultiplicatorsByBalls[view]`. The history is permanent for the ball's life: it has no cap and no drop-oldest, and leaving a gate does not remove it. `ignoreMultiplicatorCapacity` (10) is only the list's initial capacity.
6. **Bucket.** `Bucket.OnFill(filledBefore, amount)` → `Bucket.CurrentFillCount` += amount → `LevelsController.OnFillBucket(filledBefore, amount)` (static) → `TotalFillCount` += amount → on a single-mini-level level `UpdateStars(perfect, target)` → `GameScreen.FillStarEffect(startIndex, progress, pos)` → `OnBallEnterBucket` is raised (`ChunkStarBar.FillBar` on a multi-mini-level level) → `BucketCollectFX` spawned under `MiniLevelView` through `LeanPool` (§2.8).
7. **Chains.** `Chain.ChainUpdate()` is called for each ball that enters the chain trigger. `Chain.ChainCount` is incremented. When `ChainCount` reaches `UnlockNumber` (the cost), `Chain.unlocked` is set and `P_Lock` is turned off ([Inferred], §2.5).
8. **Win check.** `LevelsController.OnFillBucket` reads `TotalFillCount`. When it reaches `targetBallAmount` (the table's Target), `OnChunkAboutToBeCompleted` is raised, then `UpdateStars` runs, and `OnChunkCompleted` is raised. If there is another mini-level, `StartNextChunk()` runs (§1.4). Otherwise `Completed` = true and the flow goes to §1.4 (level complete) ([Decision] D4). `GameScreen.ShowCompleteLevelBtns` runs the moment `Completed` becomes true: the » button (`CompleteLevelBtn`, `OnClickComplete`) lets the player continue at once (R6 §4).
9. **Fail check.** `LevelsController.HandleMissionFail()` is called when `BallsController` has no balls in play (`_currentBallCount` = 0) and `TotalFillCount` < target ([Decision] D5, from the spec's "fail when no balls remain in play").

### 1.4 Level complete (stars, gems, screens, next)

1. Stars: `FilledStarCount` = 1 when `TotalFillCount` ≥ target; = 2 when ≥ perfect; the third star is not used by the rules ([Decision] D3). On a single-mini-level level `UpdateStars(perfect, target)` drives the star panel through `GameScreen.FillStarEffect` (display only, R6 §3).
2. `LevelsController.StartNextChunk()` (only if there is another mini-level): `StartMiniLevel(false)`, `OnChunkStarted` raised. `LevelChunkVisualizer` marks the finished chunk (`ActivateCheckmark`) and the new one (`ActivateDot`) (R6 §1).
3. `GameManager.CompleteLevel()` (called by `LevelsController.StartNextChunk` after the last mini-level, R7 §2): sets `LevelCompleted` = true and `gameRestarted` = false, raises `LevelControllerEnabled(false)`, adds the level score to `LeaderBoardScore`, turns the GameScreen off, plays `EndPanelClip`, and shows the `EndBlack` title card. 2 s later the card is hidden and `CompleteLevelScreen` opens. The card is also hidden on `Reset`. Turning the GameScreen off matters: `GameScreen.OnDisable` hides `StarPanel`, `BallsPanel` and `BetterThan`, which sit on the second root canvas and would otherwise draw over the complete screen. From then on `LevelsController.OnFillBucket` ignores fills, so late balls do not change the score or stars. The original also pauses physics during the 2 s; the rebuild does not (R7 §6).
4. `CompleteLevelScreen.OnEnable` locks and hides `NextLevelBtn`, sets the stars, Score, Best, the coin counter and the "Level N" title, and plays `CompleteLevelClip`. The coin panel (`GemsPanel`) stays visible. The leaderboard (`LeaderBoardView.OnEnable`) then runs the rank climb, and at its end calls `CompleteLevelScreen.ShowNextBtn()`. If the player was already first, it is called at once. `ShowNextBtn()` offers rate us on every 10th level (`CurrentLevel % 10 == 0`) and then shows and unlocks the Next button (`ShowNextBtnExtend()`, with a short punch).
5. Stars shown: `FilledStar1` always; `FilledStar2` when `FilledStarCount` > 1; `FilledStar3` when `FilledStarCount` > 2. Score is `LevelsController.TotalFillCountAcrossLevels` (this level's score), Best is `GameManager.BestScore`, both formatted with `UIUtils.ToSI`.
6. Gems: [Decision] D23: `GameManager.GemCollect(miniLevelCount)` (1 gem per mini-level, reported via `MainScreen.GetGem(miniLevelCount)`).
7. `CompleteLevelScreen.OnClickNextLevel()` (button `NextLevelBtn`) → `NextLevel()` → `GameManager.DelayedNextLevel()`.
8. `GameManager.NextLevel()`: `CurrentLevel` += 1 → `SaveData(CurrentLevel)` (§3.5) → `GameManager.Reset(increaseLevelIndex: true)` → `LevelsController.Spawn(CurrentLevel)` → §1.2.
9. Analytics: `TTPAnalyticsService.MissionCompleted(missionIndex)` and `GameManager.SendMissionCompleted(missionIndex)` ([Inferred]).

### 1.5 Level fail (restart only)

1. `LevelsController.HandleMissionFail()` → `GameManager.FailLevel()` → `GameManager.OpenFailWindow()` → `FailLevelScreen` shown. `FailLevelScreen.OnEnable` → `ballRatioText` = `TotalFillCount / targetBallAmount`.
2. The only button on `FailLevelScreen` is `RestartLevelBtn` → `FailLevelScreen.OnClickRestartLevel()` → `GameManager.RestartGame()` → `Reset(false)`, which spawns the level from the table start count. There is no continue option. There is no ad (the original's restart also waited on an ad callback, R7 §5.7).
   - `SetChunkAttempt(level, index, attempt + 1)` and `LevelAttempt` += 1 (the static fields).
   - `BallsController.SendAllToPool()` clears the old balls. `RequestSpawnInitialBalls()` spawns the row's `startBallAmount` balls at the spawn points.
   - `GameManager.gameRestarted` = true, and the main screen is switched on. The screen is the start screen, with the `Tutorial` hint on (R7 §5.7). The game screen does not open, and the counter is not set, until the player taps to start (§1.2 step 1). This follows the original's `RestartGame` (ISIL), and is a change from the earlier rebuild, which opened the game screen at once.
3. `GameScreen.OnClickRestart()` (`RestartBtn`, `Restart`) restarts the same level the same way: `GameManager.RestartGame()` (step 2), so the start screen comes up and the next tap starts the level.
4. Analytics: `TTPAnalyticsService.MissionFailed(missionIndex)` and `GameManager.SendMissionFailed(chunkIndex)` ([Inferred]).

### 1.7 Shop purchase (skin, with gems)

2. Tapping a skin: `ShopItem.OnButtonClick()` → `OnClicked(ShopItem)` → `ShopScreen.OnSelect(shopItem)` (mode 2, object argument) → `ChangeSelector(item)` → `ShopItem.SetSelected(true, enlarged: true)`. `ShopItem.SetLocked(bool)` shows or hides `LockImg`.
3. Unlock with gems: `ShopScreen.UnlockRandom()` (button `UnlockBtn`) → if `GemCounter` ≥ `ShopConfig.price` (500): `GameManager.HandleBeforeSpend(price)` → `GameManager.GemCounter` -= price → `SkinManager.GetBall(name)` → mark owned → `ShopItem.PlayUnlockAnim()` → `GemAnimationEffect.Play()` → `GameManager.SaveData` ([Decision] D26: the random pick is among locked skins; the spec does not say).
4. Not enough gems: `ShopScreen.NotAbaliableUnlockBtnClick()` shows `NotAvaliableUnlockBtn`'s text.
5. Equip: `GameManager.CurrentBallSkin` = the chosen `SkinBallItem` → `BallsController` swaps materials through `SkinBallItem.materials` (on `BallView.meshRendererCached`) ([Inferred]).

### 1.8 Colour scheme switch

1. Level load: `LevelsController.StartMiniLevel` reads the seven `ColorScheme*` columns for the row (all `Grey` today) → `ColorSchemeController.ApplySchemeForType(schemeId, type)` per `ColorSchemeItemType` → `ColorSchemeConfig.GetMaterials(type)` → each `ColorSchemeItemView.Show(material)` on its `MeshRenderer` (`_customMaterialSlotsIndexes` picks the slot).
2. Background and environment: `MaterialManager.UpdateTheme()` sets the fog meshes, skybox and `MainDirLight`/`BallsDirLight` rotation from `GameTheme` (the CrazyLabs theme list or `OriginalTheme`, chosen by `ABTestVariables.IsCrazyLabsThemes()`).
3. Player-facing scheme change: not in the code paths (Q9). In v1 only the level row chooses the scheme ([Decision] D25).
4. `IColorSchemeController.ApplyScheme(schemeId)` applies one scheme to all types. `GetItemMaterial(type)` returns the current material for `BallsController` and `MaterialManager`.

### 1.9 Settings toggles

1. Sound: `MainScreen.SoundsToggle()` (`SoundOnBtn`, `SoundOffBtn`) and `SettingsScreen.SoundsSwitch()` (`Mute`, `Unmute`) → `GameManager.SetSoundsEnable(bool)` → `AudioManager.SoundOn()` or `SoundOff()` → `isSoundsPlay` set → `SaveData`.
2. Haptics: `MainScreen.HapticToggle()` and `SettingsScreen.VibrationSwitch()` → `GameManager.SetHapticEnable(bool)` → `HapticManager.HapticOn()` or `HapticOff()` → `isHapticPlay` set → `SaveData`.
3. Privacy: `SettingsScreen.PSClick()`, `PPClick()`, `TOUClick()` → `TTPManager.ShowPrivacyPolicy()` or `ShowTermsOfUse()`. `SettingsScreen.SetPrivacySettings()` → `TTPManager.ShowPrivacySettings(closedAction)`.

### 1.10 Remote config and analytics calls

- **Remote config**: `RemoteConfigHelper.GetInt/GetBool/GetFloat/GetString(key, default)` for values (`LevelFunnel` through `DatabaseController`, A/B flags through `ABTestVariables`).
- **Analytics**: `TTPAnalyticsService.*` and `GameManager.Send*` (§3.8).

### 3.3 Ball pooling, value tiers, layers

- **Owner: `BallsPool`** (static `ObjectPool<BallView>`). Only `BallsController.Spawn` calls `BallsPool.Get`, and only `BallsController.Despawn`, `Destroy` and `SendAllToPool` call `BallsPool.Release`. Nothing else holds a `BallView` after release.
- **Prewarm** 200 (`initialPoolAmount`, both platforms). **Growth**: unlimited in v1 ([Decision] D17). The performance budget (doc 08 §7) is the test, not a cap.
- **Value tiers** [Recovered, doc 02 §2.4]: `valuePerTier` and `totalBallsForNextTier` are integer thresholds on the **total ball value** in play. The tier is the index of the first threshold above the total ([Decision] D9). `chancesToOverrideTier` is not used in v1 ([Decision] D9b). Ball value is `BallData.value`.
- **Layers** [Recovered, doc 02 §2.5]: `ballLayers` (9, 10, 11) switch on at `minimumBallsForLayers` (200, 400, 600) on the default config. iOS: layers off. A ball spawned or re-layered at count N uses the highest layer whose threshold N has passed ([Decision] D10). Layers 9, 10 and 11 do not collide with each other (doc 04 §2.6, verify in PlayMode).
- **Sizes** [Recovered]: small 0.17, medium 0.19, big 0.22 (`BallsConfig`); tier picked by the total count ([Decision] D16).

### 3.5 Save data (D14)

- **Key:** PlayerPrefs `MM3_SAVE_V1` (one JSON string). Write after each change, never per frame. Reads are wrapped in try/catch; on any failure, log `[MM3:Save]` and use defaults.
- **Schema (version 1):**

```json
{
  "version": 1,
  "level": 0,
  "gems": 0,
  "skins": { "owned": ["Ball1"], "equipped": "Ball1" },
  "settings": { "sound": true, "haptics": true },
  "attempts": { "<level>_<chunk>": 0 }
}
```

- `level` = `GameManager.CurrentLevel` (0-based on-screen index). `gems` = `GemCounter`. `skins.owned` = the `SkinBallItem.Name` values the player owns. `skins.equipped` = `CurrentBallSkin.Name`. `settings` = `isSoundsPlay`, `isHapticPlay`. `attempts` = `GetChunkAttempt` and `SetChunkAttempt` (§2.1).
- **Migration:** none in v1. A missing or invalid save starts fresh. Whether to migrate existing players' saves is the open decision D4 in `08_IMPLEMENTATION_PLAN.md` §8 (Q20).
- **Never** store keys or app IDs in the save or in code (`AGENTS.md` §5). The CrazyLabs debug save tool (`PermanentSaveConfig`) was removed from the rebuild.

### 3.7 Timing, DOTween, logging

- **Physics:** all ball and maze movement runs in `FixedUpdate` (fixed step 0.033 s). Trigger logic runs in `OnTrigger*`. `Update` is for UI, timers and camera smoothing.
- **DOTween:** visuals only. Never tween a ball's `Rigidbody` or the maze rotation with DOTween (the rotation is `RotateController`). Kill tweens in `OnDisable` and `OnDestroy`.
- **Logging:** prefix `[MM3:<Subsystem>]`. Subsystems: `Boot`, `Remote`, `DB`, `Levels`, `Balls`, `Gates`, `Chains`, `Bucket`, `Rotate`, `Camera`, `Game`, `Save`, `Shop`, `Skin`, `Colour`, `Audio`, `Haptic`, `Settings`, `Analytics`. Only errors and warnings are logged; there are no verbose or debug-only logs.

### 3.8 Analytics, and no debug code

- Analytics: call the existing wrappers (`TTPAnalyticsService.*`, `GameManager.Send*`). Do not invent new event names without the lead's approval.
- Remote config and privacy: call only through `RemoteConfigHelper` and `TTPManager`. Until the SDK is wired in, a null service stands in (`08` §5, step 8). No SDK call from gameplay code.
- No debug code (2026-11-08). The rebuild has no dev screens, cheat buttons, debug overrides, FPS overlays or debug-only logs, and no `Debug.isDebugBuild` branches. Removed: `DebugScreen`, `DebugSwitch`, `ABVariablesScreen`, `Fps`, `AdvancedFPS`, `LevelDebugData`, `LevelsController.StartBall` and `SetDynamicBallGoals`, `GameManager.DebugReset`, the `GameScreen` debug button and its unlock field (`DebugClick`, `ActivateDebugButton`), the `endBtn` ("END") button, `SettingsScreen.ABVariablesClick`, the CrazyLabs debug tools (`CrazyLabs/Extensions/DebugTools`, their prefabs and configs), the TTP log console (`TTPLogger*`, `TTPLogEventData`, `TTPAbstractViewsHolder`), `TTPTestABConfigLoader`, `ScreenshotCompanion`, `ReorderableListDebug`, `TestScript`, `TestCompression` and `RemoteConfigHelperTest`.
